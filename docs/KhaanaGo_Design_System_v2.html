Principles

Four rules that settle most design arguments. Each one comes from a finding in the pilot surveys or a user story in Chapter 2.

Say what the kitchen can doCapacity states (Available, Limited, Full, Paused) are the most consistent colour signal in the product, on customer slots, vendor meters and admin monitors.
Orange asks, charcoal answersOrange marks the one action or selection that matters on a screen. Charcoal carries text, so labels on orange stay readable.
Never colour aloneEvery state pairs its colour with an icon and a word, so the UI works in sunlight, in rain and for colour-blind users.
Same parts, different densityRiders get 64 dp buttons and 20 sp text. Vendors get dense tables. Both draw from the same tokens.

Colour

The four brand colours are fixed. Everything else (tints, text shades, status colours, dark theme) is derived so that each pairing passes WCAG AA, 4.5:1 for text and 3:1 for icons, borders and focus rings.

Typography

Plus Jakarta Sans throughout, the face already used in the project deck. It ships as a Google font, so Flutter and React use the same file. Prices and times use tabular figures so columns line up.

Rider mode scale

  • Body 20/28, buttons 20/28 at weight 800, status line 28/34

  • Maximum 3 lines of text per screen while a delivery is active

Accessibility and content

Targets the team can test against in Chapter 4.

Rules

  • Body text at least 4.5:1; large text, icons, borders and focus rings at least 3:1.
  • Targets at least 48 × 48 dp; rider status buttons 64 dp.
  • State is never colour alone: icon plus word plus colour.
  • Every interactive element has a visible focus ring in orange-700 (light) or orange (dark).
  • Every icon-only button has a spoken label, for example "Remove item" or "Open assistant".
  • Layouts survive text at 130% and do not clip at 200%.
  • Motion is optional: with "reduce motion" on, sheets and the hold fill change instantly.
  • Lists of live updates (slots, ETA) announce changes to screen readers without moving focus.

Navigation and layout

Every route belongs to a hierarchy and a user journey. Never add a new screen without specifying how users arrive, go back, and recover from an error or interruption.

CUSTOMER · MOBILE

Four destinations, short task stacks

  1. Bottom destinations: Home, Orders, Assistant, Profile (subject to approved inventory)
  2. Home → Restaurant → Menu item → Cart
  3. Cart → Delivery slot → Payment → Confirmation
  4. Orders → Live status → Receipt / support
  5. Return preserves cart and form state when safe
RIDER · MOBILE

Assignment-centric workflow

  1. Dashboard shows availability and next assignment
  2. Offer → Accept or decline when allowed
  3. Pickup details → Check-in → Collection confirmation
  4. Drop-off → Handover → Completion evidence
  5. Earnings, history, profile are secondary
VENDOR · REACT ERP

Module → list → record → action

  1. Sidebar: Overview / Orders / Kitchen / Capacity / Inventory and approved modules
  2. Header: context, role, alerts, account
  3. Workspace: list, Kanban, calendar, or form as suited to task
  4. Record actions: Save, assign, progress, export where allowed
  5. Role guards apply to routes, menus, data, and APIs

Interaction patterns

Use task-specific patterns consistently. This section adds the workflow detail that static button and color specimens cannot capture.

P01 · DISCOVERY AND PRODUCT

Search, restaurant, menu item

  • Search shows recent and suggested results, no-results recovery, and clear filters.
  • Vendor card: name, cuisine, delivery estimate, rating if available, truthful operational state.
  • Dish detail: image, price, required options, optional extras, allergen disclosure, stepper, calculated total.
  • Disabled add-to-cart explains the exact missing required choice.
P02 · CHECKOUT AND CAPACITY

No surprise charges or phantom slots

  • Keep address, cart, time slot and payment as clearly separated steps.
  • Do not treat color bands as actual booking permission; bookability must follow remaining validated capacity.
  • Expired holds show a recovery dialog and nearest permissible slots; use server time for live expiry.
  • The existing “4:32” hold countdown is an example, not the hold-time requirement.
P03 · RIDER DELIVERY

State-first task screen

  • Visible order ID, pickup, destination, next action, and verified ETA when available.
  • Hold-to-confirm for sensitive actions only when documented; provide accessible alternate confirmation.
  • Retry or queue allowed offline actions with duplicate-submission protection.
  • Show safety, privacy and support routes without crowding active delivery.
P04 · VENDOR RECORD MANAGEMENT

ERP control language

  • List: sort, query, filter, column options, pagination, row selection and bulk actions when required.
  • Record: title, status, timestamp, owner, inline details, action buttons, audit history.
  • Forms: grouped sections, clear required fields, dirty-state warning, save/cancel, field and server errors.
  • Kanban: stage counts and logical transition actions, not draggable cards unless authorized.
P05 · OPERATIONAL MONITORING

Kitchen board and capacity

  • New / Accepted / Preparing / Ready / Handed over states follow the requirements, including permitted skips or reversals.
  • Tickets emphasize promised time, allergen exclusions, item quantities and special instructions.
  • Capacity panel shows time period, units, reservations, remaining capacity and breach alerts.
  • Critical events have visual and non-color cues; notifications avoid repeated noise.
P06 · SYSTEM STATES

Every component has real states

  • Default, hover (web), focus, active, selected, disabled, loading, success, error.
  • Each data view: initial/loading, populated, empty, partial, offline, and recoverable failure.
  • Each form: untouched, invalid, valid, submitting, server-rejected, success, unsaved change.
  • Each role: authenticated, unauthorized, expired session, network loss.

Design rule: never invent a requirement

Previous UI drafts used example passwords, a sample slot countdown and placeholder field limits. Treat all unspecified values as unresolved requirements. Use the approved Chapter 2 document for acceptance criteria, not the appearance of this specimen. Maintain exact story and test-case IDs in the implementation matrix.

Build handoff & QA

A design system is successful only when screens and controls are reusable, traceable, navigable, accessible and tested against the approved requirements.

Definition of design complete

✓
Requirement-linkedEpic, story, acceptance rule and test IDs map to each screen/behavior; no ID is invented.
✓
All states designedDefault, selected, loading, empty, validation, error, disabled, offline, success and access-denied as applicable.
✓
Full navigationEvery screen has an entry route, back/exit path, focus handling and expected state persistence.
✓
Interactive implementationButtons and forms are bound to state, a local service or a real API—not styled dead ends.
✓
Readable and accessibleWCAG AA contrast, screen reader names, keyboard support, text scaling, targets and reduced motion.
✓

Traceability schema · do not change source IDs

Epic ID | Story ID | AC ID (if present) | Test Case ID | Role | Journey | Screen ID | Route | Component | State/API | Visual state | Evidence | Status | Finding / Fix
Coverage rule: Screen existence ≠ functional coverage. A story is only complete after its navigation, behavior, error and boundary conditions are implemented and independently verified. Keep COMPLETE / PARTIAL / MISSING / BLOCKED distinct.

Token naming for code

Keep token names semantic in both Flutter and React. The companion khaanago.design-tokens.json is the exchange format; do not hardcode hex values in individual screens. Use color.action.primary, color.text.primary, color.background.canvas, space.4, radius.card, and role-specific component variants.

import 'package:flutter/material.dart';
import 'package:google_fonts/google_fonts.dart';

class KhaanaColors {
  static const orange = Color(0xFFF97316);
  static const charcoal = Color(0xFF242424);
  static const cream = Color(0xFFFFF8EF);
  static const orangeText = Color(0xFFC2410C);   // orange as text on light
  static const orangeTint = Color(0xFFFFEDD5);
  static const available = Color(0xFF15803D);
  static const limited = Color(0xFF854D0E);
  static const full = Color(0xFFB91C1C);
  static const closed = Color(0xFF57534E);
  static const info = Color(0xFF0369A1);
}

ThemeData khaanaTheme(Brightness b) {
  final dark = b == Brightness.dark;
  final scheme = ColorScheme(
    brightness: b,
    primary: KhaanaColors.orange,
    onPrimary: KhaanaColors.charcoal,            // never white on orange
    primaryContainer: dark ? const Color(0xFF3A2415) : KhaanaColors.orangeTint,
    onPrimaryContainer: dark ? const Color(0xFFFDBA74) : const Color(0xFF7C2D12),
    secondary: dark ? KhaanaColors.cream : KhaanaColors.charcoal,
    onSecondary: dark ? KhaanaColors.charcoal : KhaanaColors.cream,
    error: dark ? const Color(0xFFF87171) : KhaanaColors.full,
    onError: dark ? KhaanaColors.charcoal : Colors.white,
    surface: dark ? KhaanaColors.charcoal : Colors.white,
    onSurface: dark ? KhaanaColors.cream : KhaanaColors.charcoal,
    outline: dark ? const Color(0xFF8C8379) : const Color(0xFF8A7F73),
    outlineVariant: dark ? const Color(0xFF3A3835) : const Color(0xFFEADBC8),
  );
  final base = ThemeData(useMaterial3: true, colorScheme: scheme);
  return base.copyWith(
    scaffoldBackgroundColor: dark ? const Color(0xFF1A1A1A) : KhaanaColors.cream,
    textTheme: GoogleFonts.plusJakartaSansTextTheme(base.textTheme),
    filledButtonTheme: FilledButtonThemeData(
      style: FilledButton.styleFrom(
        minimumSize: const Size.fromHeight(56),
        shape: RoundedRectangleBorder(borderRadius: BorderRadius.circular(12)),
        textStyle: const TextStyle(fontSize: 16, fontWeight: FontWeight.w700),
      ),
    ),
    inputDecorationTheme: InputDecorationTheme(
      border: OutlineInputBorder(borderRadius: BorderRadius.circular(12)),
      contentPadding: const EdgeInsets.symmetric(horizontal: 14, vertical: 14),
    ),
    cardTheme: CardThemeData(
      elevation: 0,
      shape: RoundedRectangleBorder(
        borderRadius: BorderRadius.circular(16),
        side: BorderSide(color: scheme.outlineVariant),
      ),
    ),
  );
}
